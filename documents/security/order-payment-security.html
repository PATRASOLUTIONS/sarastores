Order and payment security verification

14 October 2026. Bounded source, handler and isolated database verification. No live customer records, actual payment transactions or real email deliveries were used.

Credentials alone are not a deployment guarantee. Real Razorpay, Pine Labs and Paytm UAT, public HTTPS return/webhook registration, MongoDB transaction support, SMTP delivery, monitoring and approved production smoke tests remain necessary. This is not an exhaustive penetration-test certificate.

Confirmed vulnerability and remediation

SeverityFindingRemediation
High, 10/10 confidenceStore-restricted order staff could read, confirm or delete another store's orders and obtain its invoice/license data. List filtering did not protect individual routes.Shared live store authorization covers lists, detail reads, updates, deletion, invoices, license assignment and bulk mutation. Store predicates are carried into database mutations and transactional license claims. Unauthorized reads return 404 without disclosing order existence.

Full administrators, explicitly all-store staff, permitted-store staff, owning customers and valid guest capability holders retain their intended access. Dashboard access alone does not grant order permissions. Revoked or deactivated accounts are rechecked from live identity records.

Private order responses and invoices use Cache-Control: private, no-store. Customer-facing detail responses and update acknowledgements omit guest capability hashes. Staff email copies now obey store scope and contain only an order number and total, not customer identity, addresses, license keys or payment proofs.

Configure confirmed-order emails

  1. Sign in as an admin or superadmin.
  2. Open Admin > Sales > Order Notifications, at /admin/order-notifications.
  3. Enter an authorised business email address, select Enable confirmed-order emails, and save. Reloading retrieves the persisted value.
  4. Confirm an order in Admin Orders, or complete verified Razorpay, Pine Labs or Paytm checkout. The additional recipient receives a short confirmation summary. The original customer notifications continue.
  5. Disable the checkbox to stop the additional recipient. Existing manager/store copies remain subject to their own authorised rules.

The setting is stored in the private order_notification_settings collection, not public storefront settings. Its API and server-rendered page require full-admin access. Invalid emails and unexpected input fields are rejected. Saving settings does not test SMTP delivery. Pending, failed and payment-review transactions do not trigger confirmed notifications.

An atomic per-order adminNotifications.confirmed claim prevents repeated callbacks, concurrent requests or later status reversals from sending another admin confirmation. Paid software orders still receive their confirmation when immediate fulfillment has already changed the order to delivered. SMTP delivery does not delay hosted software fulfillment.

Delivery limitation: SMTP cannot guarantee exactly-once delivery across process crashes. Delivery outcomes are recorded as sending, sent or failed; unexpected failures are explicitly logged. A stale sending record is ambiguous. An operator must inspect logs and SMTP acceptance before any manual resend; failed or ambiguous claims are not automatically retried. Settings changes do not bulk-email historical orders.

Remaining external gates

Obtain the separately issued Pine Labs callback signing key and your own Paytm merchant credentials. Register the public HTTPS callbacks/webhooks with each gateway and run actual gateway UAT for success, decline, pending, delayed confirmation and replay. Configure SMTP and verify delivery to the chosen business inbox. Preserve operational monitoring for notification failures and payment-review orders.

See Website payment gateways for environment-variable names and provider setup. Do not use merchant credentials found in public posts or paste secrets into reports.
