# Cart and purchase validation

Implemented 2026-10-26. No tests, TypeScript checks or builds were run, following the user's instruction to stop testing. Validation below describes the implementation and manual code review, not tested results.

Product availability now requires an active catalogue entry and rejects disabled, deleted, discontinued, draft, archived and out-of-stock entries. Unknown, malformed or missing tracked stock fails closed. Software may use its available-key count; only software explicitly marked `trackInventory: false` is treated as untracked inventory.

Quantities must be positive whole numbers, with a default maximum of 1,000 units per product and any lower catalogue `maxPurchaseQuantity`. Zero, negative, fractional, boolean and oversized quantities are rejected. Stock and purchase caps apply to the total across a product's cart lines, preventing option splitting from bypassing the limits. Existing limits of 20 purchase lines and ₹10 lakh remain enforced by server pricing.

Cart lines have a stable key containing the product and selected options. Matching options merge; different color, size, SKU, RAM/storage and software options remain distinct in local merges, sign-in cart handling, cart selection, quantity updates, removal and checkout. The existing storefront resolves RAM/storage variants to their own catalogue product IDs/SKUs. Unknown standalone `variantId` values are rejected; a client cannot create a differently priced variant by supplying arbitrary metadata.

Add-to-cart uses a synchronous shared lock per account and purchase option, followed by a 500 ms duplicate-click guard. Quantity controls ignore repeated changes within 300 ms and repeated identical values. Encoded line keys prevent a second removal click from falling back to a different variant of the same product. Adding rechecks current catalogue price, stock and active state before committing. Cart changes update the shared ref immediately, and account writes run sequentially. Removing or reducing a saved item remains possible if another retained item is unavailable; this does not allow adding or increasing unavailable selections.

Cart availability refreshes while visible, on focus and every 30 seconds. Checkout performs a fresh read-only `/api/cart/validate` call before payment or store submission. It derives identity from the session, supports guests, recomputes prices, coupons, rewards, tax and shipping, and asks the shopper to review changed totals before retrying. Cart changes invalidate a previous quote. The final order transaction revalidates the catalogue and price fingerprint before insertion.

Server pricing ignores client money fields. Unit prices and totals use two-decimal currency rounding; gross value is accumulated in minor units, and rounded GST plus the tax-exclusive subtotal equals the gross amount. Payment, coupon, order and pay-at-store controls use synchronous submission guards. Empty carts cannot proceed.

These changes validate the current inventory snapshot. They do not introduce inventory reservation between simultaneous shoppers, replace the SAP inventory feed, or change cancellation/restocking behavior. Existing payment-intent claims still protect paid orders from reusing the same payment; this change does not add a new API idempotency contract for anonymous cash-on-delivery retries.

Payment initiation uses a direct server-side Razorpay Orders request with a 15-second timeout and no automatic retry. This avoids the installed SDK's error handler, which assumes network failures contain an HTTP response. Credentials are trimmed, payments below ₹1 are rejected before contacting the gateway, and returned currency and amount must match the server quote. Authentication, gateway availability, amount rejection and checkout-intent persistence failures have distinct customer messages; gateway diagnostics redact configured credentials. Software option fields are retained in the payment request. The reported Pay Now failure's original runtime cause remains unconfirmed: no current server error or gateway response was accessible, and no payment attempt or automated checks were run.
