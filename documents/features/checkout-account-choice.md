# Checkout account and saved-cart choice

Implemented 2026-10-25. Tests, TypeScript checks and production builds were not run, following the user's instruction to stop testing.

Visitors can add products without an account. Checkout offers sign-in or guest checkout. Guests must supply a name, email, Indian mobile number and full address, including city, state, pincode and country. The same guest-detail schema is enforced by order creation and pay-at-store requests; guest pickup also collects the customer's address separately from the collection store.

Contact validation now requires both first and last name, a valid email with a recognized public domain, and a 10-digit Indian mobile number starting with 6–9 for every checkout. Name fields reuse registration's Unicode and typing-error checks. Errors appear beside the fields while typing and on blur, and invalid contact details block address use, saving and payment. The server enforces the same contact schema for both guest and account orders and store-payment requests. Existing saved addresses without a surname remain readable, but checkout asks the shopper to fill it in before placing a new order.

The checkout sign-in button preserves the current cart in tab storage and returns to `/checkout`. Immediately after sign-in, the authenticated cart loader saves both the current products and the previous account cart to the account. A popup displays the previous items and asks the shopper to include them in this purchase or move them to the wishlist. Including combines quantities for products already present; moving preserves the current products and saves previous product IDs to the wishlist. Payment remains blocked until the choice succeeds. An empty previous cart continues automatically.

Closing the popup, choosing "Keep both in cart", or navigating away from checkout retains both sets in the account cart. Manual logout waits for the cart preservation request; a failed save blocks logout and asks the shopper to retry. Local account storage holds the combined cart while the popup is open, and tab storage retains the separate current items for retrying. Cart updates from storage cannot replace the current purchase with the combined cart while a choice is pending.

The authenticated `/api/cart/checkout-selection` handler derives account identity from the session and saves a draft containing the two original selections before showing the popup. Stored cart prices are display hints. Final selection checks that the saved cart still matches the displayed snapshot, recalculates purchase prices and quantities on the server, and commits cart and wishlist changes in one MongoDB transaction. A concurrent saved-cart change returns 409 and asks the shopper to review their cart. Failed changes retain the pending choice and the combined saved cart. This route requires MongoDB transaction support, consistent with the platform's existing transactional operations.

A tab-scoped request ID is saved with the cart choice. Retrying preservation or a choice after a lost response returns the saved draft or already committed choice instead of adding the previous quantities twice.

Software products moved from the saved cart are also returned by wishlist loading and can be added back with their software product type. Hidden hardware and inactive software remain subject to catalogue visibility rules.

Each checkout product now has visible "Move to wishlist" and "Remove" buttons. Removal uses the existing confirmation popup. Moving an item saves it to the signed-in customer's wishlist before removing it from the checkout cart; an already-wishlisted item also counts as saved. Failed wishlist requests leave the item in the cart. Guests receive a sign-in message and retain their item. Hardware and active software are supported. Checkout actions are blocked while the move is saving, and totals follow the updated cart.

Checkout contact and address inputs, address editing/selection, guest choice and typed coupon code are saved in a tab-scoped `sessionStorage` draft. Refreshing or reopening checkout in the same tab restores unfinished input before account autofill runs, including intentionally cleared fields. Drafts are scoped to the guest or signed-in account; the explicit checkout sign-in handoff can carry a guest draft into the account. A successful order or hosted payment confirmation clears that account's draft. Drafts contain no trusted totals, discounts, payment credentials or payment status; address validation and server pricing still run before submission. Browser storage failures leave the form usable in memory.
