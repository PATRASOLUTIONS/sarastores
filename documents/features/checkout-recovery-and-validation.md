# Checkout recovery and validation

Updated 2026-10-26. Source review only: tests, TypeScript checks, builds and live payment/inventory operations remain stopped under the user's earlier instruction. This document describes implemented behavior, not a runtime certification.

Home delivery validates overall catalogue stock and offers every configured online gateway. Pickup validates each canonical hardware item code against the selected active retail store's store code, then lists only stores holding the whole requested cart. Pickup offers online gateways plus Pay at Store when enabled. Warehouses and inactive locations cannot be pickup destinations. Current product status, quantities, purchase caps, prices, tax, shipping, coupons and rewards are checked on the server. The client sends the displayed amount only as a consistency check; a changed total stops payment initiation for review.

Payment and order APIs independently validate customer contact fields. Delivery additionally requires a valid address and a currently supported delivery region/pincode. Guests require the full customer form for either fulfilment mode. Pickup metadata and shipping address are derived from the stored location.

Checkout drafts are scoped to the guest or account and saved in local and session storage. They retain unfinished contact input, edited fields, address selection, fulfilment/store, payment gateway, coupon selection, rewards choice, store-payment request and unfinished transaction details. Restoration reads the newest valid copy before saving begins. Discounts are recalculated rather than trusted from storage. A storage failure produces a visible warning. Explicit checkout sign-in carries the guest form into the account draft without replacing an existing account draft when no guest draft exists.

Razorpay success saves the signed receipt and original order snapshot before verification/order creation. If either step fails, checkout retains a Recover payment action and blocks another payment. Server recovery requires the same session owner and checkout capability. A committed checkout returns the existing order without creating another or repeating redemption/notifications; the guest capability can reproduce its order-access link. Hosted gateway references and purchased-item snapshots are retained in both browser stores and are cleared only after a confirmed completion or confirmed failure. Unknown or pending status blocks another payment.

Successful checkout subtracts purchased quantities by cart-line identity instead of clearing the whole cart, retaining other items and quantities added while payment was pending. A per-owner/order completion marker prevents repeated callbacks from subtracting again. Account changes cannot debit another user's cart. A browser crash between writing that marker and saving the cart may retain purchased items; it favors retaining data over deleting items twice.

Remaining limits: no inventory reservation/decrement between concurrent shoppers is introduced; the SAP inventory and cancellation/restocking flow still needs that integration. Browser storage can be disabled, cleared or lost, and drafts are local to that browser. Razorpay recovery begins when its success callback delivers a signed receipt; closing before that callback can require support/provider reconciliation. Expired incomplete payment capabilities, prices/stock changed after payment, and legacy hosted records without an item snapshot may require reconciliation. True simultaneous cross-tab cart updates are not an atomic server merge. Automated and isolated runtime checks are required before asserting production readiness.
