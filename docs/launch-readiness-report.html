02Launch blockers

Three items must be resolved in the Vercel production environment before go-live. None require code changes.

B1. Razorpay is configured with a TEST key Blocker

RAZORPAY_KEY_ID currently starts with rzp_test_. In test mode Razorpay accepts payments but never moves real money — customers would complete checkout and receive an order, and you would be paid nothing.

Action: set RAZORPAY_KEY_ID (rzp_live_…) and RAZORPAY_KEY_SECRET to the live pair in Vercel → Production. No code change needed; the client key is served to the browser from /api/payment/create-order, so there is no separate NEXT_PUBLIC_ key to update. Confirmed live keys are available.

B2. No SMTP configuration — every transactional email silently fails Blocker

SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS and EMAIL_FROM are all unset. lib/email.ts builds its Nodemailer transport straight from those variables, so every send throws.

Because every send site is wrapped in try/catch, nothing crashes — which is worse: orders succeed, the customer is told to check their inbox, and no message is ever delivered. This affects order confirmations, the signup verification link, password resets, contact-form notifications, the vendor/admin order alerts and the newsletter.

Action: set all five variables plus CONTACT_ADMIN_EMAIL. Note the variable is SMTP_PASS — .env.example wrongly calls it SMTP_PASSWORD. Confirmed credentials are available. Send one live test order after deploying.

B3. NEXT_PUBLIC_SITE_URL is unset Blocker

27 files read this variable. With it unset the fallback chain resolves to VERCEL_URL (the per-deployment *.vercel.app hostname) or http://localhost:3000, depending on the file. Consequences:

  • Email verification and password-reset links point at http://localhost:3000 — new customers could never verify an account.
  • Every SEO canonical, the sitemap, robots.txt and all OG/Twitter images resolve to the Vercel preview domain instead of the real one — Google would index the wrong hostname.
  • The Google OAuth redirect URI would not match what is registered.

Action: set NEXT_PUBLIC_SITE_URL, NEXT_PUBLIC_APP_URL and NEXTAUTH_URL all to https://sarastores.com. NEXT_PUBLIC_APP_URL is currently pinned to http://localhost:3000 and must be changed.

A complete, verified variable list has been written to .env.production.example. It was derived from actual process.env usage in the code, not from the stale .env.example.

03Issues found and fixed in this pass

Eight items. Each was verified after the change.

1. Live database credentials hardcoded in five scripts Critical

Five files contained a full MongoDB Atlas connection string with the username and password inline — admin:admin on the same cluster and the same e-commerce-bytewise database the production application uses. Anyone with a copy of the source had complete read/write access to live customer, order and payment data.

Fixed in inspect_order.js, scripts/backfill-descriptions.js, scripts/mark-all-in-stock.js, scripts/seed-brands.js — each now reads process.env.MONGODB_URI and exits with an error if it is absent. Two further scripts (seed-database.js, migrate-manufacturer.js) silently fell back to mongodb://localhost:27017, which risked seeding or migrating the wrong database entirely; those fallbacks were removed too.

Action still required — removing the strings from the source does not un-leak them. The admin / admin credentials on that cluster must be rotated in MongoDB Atlas before launch, and Atlas network access should be restricted to the Vercel egress ranges. Treat those credentials as compromised: they are weak, guessable, and have been sitting in plaintext in the project folder.

2. Employee-ID enumeration oracle Medium

POST /api/employees/validate is public by design — in-store checkout runs before login — but it had no rate limit. It answers {"valid":true} with the employee's name for a correct ID, so the entire staff list could be brute-forced from the open internet, then used to claim employee pricing.

Fixed in app/api/employees/validate/route.ts: wrapped in withRateLimit at 20 attempts per 15 minutes per IP. The handler also echoed raw exception messages back to the caller and logged full employee records to the server console; both were removed. Verified: requests 1–20 return 200, requests 21–25 return 429.

3. Deactivated products were publicly listable Medium

include_inactive=true was honoured for anonymous callers on /api/products, /api/products/[id] and /api/products/bulk. Any visitor could enumerate withdrawn or unreleased SKUs together with their pricing. 14 deactivated products were exposed this way at the time of testing.

Fixed: the flag is now gated behind isAdmin() in all three routes and ignored for everyone else. Verified after the change — an anonymous caller receives 654 products with or without the flag, while an authenticated admin still receives all 668 and both /api/products/[id] and /api/products/bulk continue to answer 200 for staff. This interacted with the CDN — see item 4.

4. CDN would have cached the admin catalogue response publicly High

vercel.json applied Cache-Control: public, s-maxage=60 to /api/products(.*) — every path under it. Because the edge cache is keyed on URL and not on the session cookie, an administrator's ?include_inactive=true response would have been stored at the edge and served to the next anonymous visitor requesting that URL, re-opening item 3 through the cache. The reverse ordering would have handed the admin a stale public response and made deactivated products vanish from the admin product list for up to a minute.

Fixed in vercel.json: the public caching rule now carries "missing": [{"type":"query","key":"include_inactive"}], and a second rule serves private, no-store whenever that parameter is present. Storefront caching is unchanged; only the privileged variant bypasses the edge.

5. Wildcard CORS combined with credentials Medium

/api/products/bulk reflected the caller's Origin header back in Access-Control-Allow-Origin while also sending Access-Control-Allow-Credentials: true. That combination lets any website on the internet make cookie-bearing requests to the endpoint and read the response.

Fixed in app/api/products/bulk/route.ts — credentials are no longer accepted and the origin is a plain *, which is safe once credentials are off. This was the only route in the application with that header combination.

6. Site URL fell back to an unrelated domain Medium

lib/seo.tsx declared https://bytewise.shop as the fallback site URL — a different project's domain, left over from a template. With NEXT_PUBLIC_SITE_URL unset it would have been emitted in the site's JSON-LD structured data. Two marketing modules used a third domain, saraelectronics.in.

Fixed: lib/seo.tsx, lib/marketing/campaigns.ts and lib/marketing/email-layout.ts now all fall back to https://sarastores.com, matching the store-QR modules. Setting NEXT_PUBLIC_SITE_URL (blocker B3) makes the fallback moot, but the values should not disagree.

7. No production environment template existed Process

.env.example is unusable: every line is commented out, it names SMTP_PASSWORD where the code reads SMTP_PASS, and it omits most variables the application actually reads. Deploying from it would have produced exactly the three blockers above.

Added .env.production.example, derived from real process.env usage, with each variable annotated with what breaks when it is missing.

8. Corrupted build directory produced a false build failure Tooling

The first production build failed with TypeError: Cannot read properties of undefined (reading 'call') while prerendering /_not-found. This was not a code defect: the dev server and next build were both writing to the same .next directory.

Resolved by stopping the dev server and deleting .next. The clean rebuild succeeded. Worth knowing for deployment: always build from a clean .next. Vercel does this automatically, so this will not recur in CI.

08Open risks accepted for launch

Known and understood. None of these block go-live, but R1 and R2 need an operational answer on day one.

R1. Stock is never decremented when an order is placed Business-critical

lib/order-pricing.ts validates availability at checkout, but app/api/orders/route.ts writes the order without reducing any inventory count. The code comments this as waiting on the SAP inventory feed. The practical effect is that a single unit can be sold repeatedly and the storefront will keep showing it in stock.

Mitigation until the integration lands: watch order volume against real stock manually, especially on high-demand festival lines. This is the single most important functional gap in the platform.

R2. Orders can be created without payment High

/api/orders defaults paymentMethod to "cash" and writes the order with status pending. There is no cash-on-delivery option in the checkout UI, so this is not reachable through normal use — but any authenticated customer can post directly to the endpoint and create unpaid pending orders.

Money itself is safe: totals are always recomputed server-side from the database by computeOrderPricing(), and Razorpay payments are verified for both capture status and amount before an order is marked confirmed. The risk is junk orders, not lost revenue. Treat pending + cash orders as unverified until reviewed.

R3. Rate limiting is in-memory Medium

Both limiters store counters in a module-level object. On Vercel every serverless instance has its own copy and counters reset on cold start, so a distributed attacker gets roughly 5 attempts per instance rather than 5 overall. It stops casual abuse, not a determined botnet.

Proper fix is a shared store (Upstash Redis integrates in under an hour). Worth doing soon after launch. Setting RECAPTCHA_SECRET_KEY would also help — reCAPTCHA verification is skipped entirely while that variable is unset.

R4. The build ignores type and lint errors Medium

ignoreBuildErrors and ignoreDuringBuilds are both enabled, so a broken deployment can ship. npm run lint is also non-functional — no ESLint config or dependency is installed — and there is no automated test suite of any kind.

Until that changes, npx tsc --noEmit is the only real gate and must be run manually before every deploy. The current baseline is 48 errors; treat any increase as a regression.

R5. Catalogue data inconsistencies Low

Sub-category and brand labels are stored inconsistently — TV 55" versus TV 55, GODREJ versus Godrej, Refrigerators versus REFRIGERATOR. Filtering code works around this today, but each new workaround is a place for a bug to hide.

A normalisation migration is the real fix. Cosmetic for launch.

R6. Repository hygiene and test data Medium

order_dump.json and order_debug_dump.json sit in the project root and contain real order data. They are not referenced by the application and are not covered by .gitignore. Several other one-off debug scripts (audit-ids.js, exhaustive-audit.js, check-assignments.js, inspect-*.js) are also leftovers.

Recommend deleting the two JSON dumps before the source is shared or committed anywhere — they are personal data. A test order, SARAECOM-00100125 (₹46,100, status pending), also remains in the live database and should be removed before launch so it does not appear in reporting.

09Deployment checklist

In order. Steps 1–4 are the blockers.

  1. Rotate the MongoDB Atlas credentials. The admin/admin pair is compromised. Create a new user with a strong password, update MONGODB_URI, and restrict Atlas network access to Vercel's egress ranges rather than 0.0.0.0/0.
  2. Set the live Razorpay keys — RAZORPAY_KEY_ID (rzp_live_…) and RAZORPAY_KEY_SECRET.
  3. Set SMTP — SMTP_HOST, SMTP_PORT, SMTP_USER, SMTP_PASS, EMAIL_FROM, CONTACT_ADMIN_EMAIL. Remember it is SMTP_PASS, not SMTP_PASSWORD.
  4. Set the URLs — NEXT_PUBLIC_SITE_URL, NEXT_PUBLIC_APP_URL and NEXTAUTH_URL all to https://sarastores.com.
  5. Copy the remaining variables from .env.production.example: SESSION_SECRET (≥32 chars), CRON_SECRET, and the reCAPTCHA pair if bot protection is wanted.
  6. Confirm ENABLE_DEBUG_ROUTES is false or absent.
  7. Point the sarastores.com DNS at Vercel and confirm the TLS certificate is issued before announcing.
  8. Wire the /api/cron/* routes to Vercel Cron. Nothing is scheduled today — vercel.json has no crons block and the node-cron import in instrumentation.ts is commented out, despite the log line claiming otherwise. Cart-recovery and wishlist alerts will not run until this is done.
  9. Delete the two order JSON dumps and the SARAECOM-00100125 test order.
  10. Run npx tsc --noEmit and confirm the count is still 48.

Smoke test on the live domain, immediately after deploy

  • Register a new account and confirm the verification email arrives with a sarastores.com link.
  • Place one real low-value order end to end and confirm the money reaches the Razorpay live dashboard.
  • Confirm the order confirmation email arrives.
  • Log in as admin and confirm the order appears in /admin/orders.
  • Submit the footer newsletter form and confirm the address lands in admin Leads.
  • Fetch https://sarastores.com/robots.txt and /sitemap.xml and confirm they reference the real domain.
  • Confirm https://sarastores.com/api/debug/session returns 404.

10Methodology and limits

What was actually done, and what this report does not cover.

Performed: a static scan of 853 project files (excluding dependencies and build output) for hardcoded secrets, unguarded mutating routes, debug-route gating and XSS sinks; live anonymous probing of 30 privileged endpoints with mutating verbs; brute-force testing of login, signup and employee validation; end-to-end functional testing of the newsletter including duplicate and invalid input; a full environment-variable audit against real process.env usage; review of next.config.mjs headers and vercel.json caching and CORS rules; manual review of every dangerouslySetInnerHTML site; a clean production build; and a TypeScript check before and after every change.

Not performed: no penetration test by a third party; no load or stress testing; no dependency CVE audit (npm audit was not run as part of this pass); no cross-browser testing beyond Chromium; no verification of Razorpay live-mode behaviour, which cannot be tested until live keys are in place; and no email deliverability testing, which is impossible until SMTP is configured. Payment verification logic was read and reasoned about but only exercised against Razorpay test mode.

All testing ran against the development server on localhost:3005 connected to the live production database. Probes were deliberately non-destructive — they used non-existent ObjectIds and empty payloads, and every privileged call was rejected before reaching a write. The newsletter test created one row in leads, which can be removed from admin Leads.
