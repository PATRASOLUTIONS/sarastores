Verdict — the responsive system is in good shape. Of 84 pages, only two had a genuine layout failure, and the underlying cause of both has been fixed. A third, more serious defect was found outside the standard breakpoints: every page on the site scrolled horizontally between 1024 px and ~1045 px — the width of an iPad Pro 11" in portrait. That is now fixed. Touch targets have since been brought up to WCAG 2.2 AA across the storefront and admin, and every icon-only control now has an accessible name. Re-verified after all changes: 0 px overflow at 360, 390, 768, 1024, 1280 and 1920 px across representative storefront, account and admin pages.
Scope limit — all measurements were taken in Chromium only. Safari/WebKit and Firefox/Gecko were not tested, so this is a responsive-layout report rather than a full cross-browser compatibility certification. See Browser coverage.

03Layout bugs found and fixed

1. Whole site scrolled horizontally at 1024–1045 px High — affected every page

At exactly the lg breakpoint the header revealed its “Wishlist” and “Cart” text labels, which grew the right-hand cluster to 524 px. Because that cluster is flex-shrink-0, it could not give the space back, so the document became wider than the viewport and the entire page scrolled sideways — 21 px over at 1024 px, 4 px at 1040 px, clean from about 1045 px.

This window is not obscure: 1024 px is iPad Pro 11" portrait and the low end of many small laptops. It was missed by the standard breakpoint set because 768 px and 1280 px both sit outside the failing range.

Fixed in components/Header.tsx — the two labels moved from lg:inline to xl:inline, so the compact icon-only header persists until there is genuinely room. Re-verified at 1000/1024/1040/1180/1280 px across 14 pages: 0 px overflow everywhere.

2. /account and /account/dashboard rendered two headers and two footers High

app/account/layout.tsx wraps every account page in AccountClientShell, which already renders <Header>, <main> and <Footer>. Both pages rendered their own set as well, so visitors saw the header twice, the footer twice, the “My Account” hero twice, and two nested <main> landmarks (invalid HTML and a screen-reader problem).

The nested header was confined to the shell's narrower content column, so it could not fit — producing +170 px overflow at tablet and +141 px at laptop.

Fixed in app/account/page.tsx and app/account/dashboard/page.tsx — the duplicated chrome was removed and each page now returns only its own content. Re-verified: exactly 1 header, 1 footer, 1 <main>, and 0 px overflow at all five widths.

3. Account dashboard order count never rendered Medium

Found while fixing the above. getOrders() returns a Promise, but the result was passed straight into setOrders() without awaiting, so orders held a Promise and orders.length evaluated to undefined — the “Orders” statistic rendered blank.

Fixed in app/account/dashboard/page.tsx — the call is now awaited inside a cancellable effect with an array guard and error fallback.

4. Dead links in the account sidebar Medium

The shell's navigation listed /account/wishlist, /account/addresses, /account/payment-methods and /account/settings — none of which exist, so all four returned 404.

Fixed in app/account/account-client-shell.tsx — links repointed to /dashboard/wishlist and /dashboard/settings; “Payment Methods” removed because no such feature exists anywhere in the codebase.

5. Touch targets below the accessibility minimum Accessibility

Measured at 360 px against WCAG 2.2 AA (2.5.8), which requires 24 × 24 CSS px, counting only real controls. The worst offenders were the brand-page carousel dots at 32 × 8 px and the admin “Open sidebar” button at 22 × 40 px, which appeared on every admin page.

Fixed by enlarging the hit area while leaving the visuals untouched — the carousel dots keep their pill appearance inside a 24 × 24 button, and the admin chrome moved to 44 × 44. Filter accordions, “Clear All”, “+ Show More” and the delivery-location trigger were raised from 20–23 px to a 24 px minimum, and the product-card wishlist button from 28 to 32 px.

Files: the four brand landings, app/brands/[slug]/page.tsx, components/AdminSidebar.tsx, components/AdminHeader.tsx, components/DeliverToPincode.tsx, components/products/ProductListingCard.tsx, app/products/page.tsx. Re-verified at 360 px: /, /bosch, /lg and /admin/dashboard report zero controls below the minimum; /products fell from 21 to 0.

6. Icon-only controls had no accessible name Accessibility

The banner previous/next arrows on all four brand landings, the carousel dots, and the admin mobile search toggles were unlabelled — a screen reader announced them only as “button”.

Each now carries an aria-label, and the dots also expose aria-current so the active slide is announced. Verified: /bosch and /lg report 0 unlabelled buttons, down from 2 each.

04Open issues

1. /subham reports a 4 px scroll width at mobile Low — cosmetic

At 360 px and 390 px the document measures 4 px wider than the viewport. A clip-aware re-scan found zero unclipped elements extending past the edge — the decorative blur circles are already contained by an overflow-hidden hero section.

This is a sub-pixel compositing artefact from the stacked blur-3xl layers, not a layout error. Nothing is visually cut off. Left as-is rather than risk a speculative change to a working page.

2. Safari and Firefox remain untested Medium

Every measurement in this report was taken in Chromium. See section 07 for the specific WebKit risks this could not rule out.

08Methodology & caveats

How each page was measured

  • Loaded once, then resized through all five widths so CSS media queries re-evaluated without a reload.
  • Overflow = documentElement.scrollWidth − clientWidth, with the true CSS width read in-page each time (the browser applied a 90 % zoom, which was compensated for).
  • Offending elements identified by walking the DOM for anything whose right edge passed the viewport, excluding elements inside horizontally-scrollable carousels and, on re-scan, anything clipped by an overflow-hidden ancestor. Without those exclusions the intentional category rails produce false positives.
  • Touch targets measured from live bounding boxes at 360 px, restricted to genuine controls.
  • Results written to browser storage after each page so a slow or failed page never lost earlier work.
  • npx tsc --noEmit run after every code change — the count fell from 71 to 48 across this work and never rose.

Caveats — read before quoting this report

  • Chromium only. No Safari or Firefox verification.
  • Layout geometry, not visual design. The audit detects overflow, breakpoint failures and target sizes. It does not judge spacing, typography, colour contrast or whether a page matches its intended design.
  • No real devices. Emulated widths only — no touch input, no device pixel ratio, no mobile GPU or network conditions.
  • Content was sampled 2–3 s after load. A few data-heavy pages (/cart, /checkout, /software, /vendor/dashboard) showed little main-region text at that instant. These are empty-state or async-loading conditions, not layout failures.
  • Dynamic routes were not included in the 84 — product, category and brand detail pages were covered functionally in the platform audit but not re-measured at every breakpoint.
  • Measured while signed in as an administrator, so the header showed the logged-in variant throughout.
